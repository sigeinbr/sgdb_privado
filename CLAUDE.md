# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Sobre o projeto

Repositório de migrações de banco de dados do **sgdb_privado** — o banco de dados dos
produtos para **empresas privadas**, irmão do projeto `sgdb`/Sigein (que serve órgãos
públicos, com isolamento multi-tenant por Unidade Gestora/`ug_id`). Aqui o isolamento
multi-tenant é por **Conta** (`conta_id` / `adm.contas`) — uma empresa privada cadastrada
via autoatendimento, não provisionada manualmente por um administrador. Contém
exclusivamente scripts SQL gerenciados pelo **Flyway**, que versiona e aplica as
alterações em um banco **PostgreSQL 15**. Não há código de aplicação aqui — somente DDL,
DML de configuração e lógica de banco (triggers, functions, views).

Este repositório nasceu de uma cópia adaptada da estrutura de `adm`/`audit` do Sigein.
Os demais schemas do Sigein (`comum`, `patrim`, `integracao`, `invent`, `pncp`) **não**
foram copiados — só existem aqui se e quando um módulo equivalente para empresas privadas
for desenvolvido.

## Comandos

### Conectar ao banco de dados

```bash
docker exec postgres-sigein psql -U sgidba -d target -c "SEU SQL"
# Sessão interativa:
docker exec -it postgres-target psql -U sgidba -d target
```

### Aplicar migrations (Flyway)

```bash
# Pré-requisito (uma vez só): banco "target" precisa existir em postgres-sigein — ver
# seção "Infraestrutura local" abaixo.

# Aplicar Scripts/ (só sobe o serviço flyway, que entra na rede do sgbd):
docker compose up -d

# Forçar re-execução do Flyway sem recriar o banco:
docker compose restart flyway

# Ver log das migrations:
docker logs flyway-target
```

### Verificar estado das migrations

```bash
docker exec postgres-sigein psql -U sgidba -d target -c \
  "SELECT version, description, success, installed_on FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 20;"
```

## Estrutura de diretórios

- `Scripts/` — migrations versionadas aplicadas pelo Flyway (fonte da verdade)
- `Scripts/ajustes_pontuais_*.sql` — scripts sem prefixo `V` executados manualmente, fora do Flyway (convenção herdada do Sigein, ainda sem uso neste repositório)

## Convenção de nomenclatura das migrations

Formato obrigatório: `V{YYYYMMDDHHMI}__{descricao_com_underscores}.sql`

Exemplos:
- `V202608101000__privado_initial.sql`
- `V202609011400__criar_tabela_planos.sql`

O Flyway não reaplica scripts já executados. Nunca editar um script já aplicado — sempre
criar um novo.

## Arquitetura de schemas

| Schema | Finalidade |
|---|---|
| `adm` | Administração: usuários, contas, módulos, menus, grupos de permissões, tokens, consultas, relatórios |
| `audit` | Espelho de auditoria de todas as tabelas de negócio de `adm`, mais `audit.log_acessos` |

Novos schemas de módulo (equivalentes a `patrim`/`comum`/etc do Sigein) entram aqui
somente quando um produto para empresas privadas precisar deles — não antecipar.

## Padrão de tabelas

### Campos de auditoria (obrigatórios, sempre primeiro)

```sql
created_by  varchar(50) default current_user not null,
created_at  timestamp(0) default current_timestamp not null,
updated_by  varchar(50) default current_user not null,
updated_at  timestamp(0) default current_timestamp not null,
deleted_by  varchar(50) null,   -- exclusão lógica
```

### Multi-tenant por Conta (`conta_id`)

Tabelas que variam por conta seguem o padrão:

```sql
conta_id  integer not null references adm.contas,
id        integer not null,
primary key (conta_id, id)
```

Tabelas globais (sem variação por conta, como `adm.contas`, `adm.modulos`) usam
`id serial primary key` ou `id integer generated by default as identity`.

### Geração automática de ID (`adm.func_id_before`)

Tabelas com `conta_id` não usam sequences. O ID é gerado pela trigger `id_bi` via
`adm.func_id_before()`, que faz um UPSERT em `adm.contas_sequencias` (contador
serializado por `conta_id` + nome da tabela).

```sql
create trigger id_bi before insert on schema.tabela
  for each row execute function adm.func_id_before();
```

Isso é uma evolução deliberada em relação ao Sigein original, que calculava
`MAX(id) + 1` filtrado por `ug_id` — correto para UGs provisionadas manualmente uma a
uma, mas sujeito a corrida sob inserts concorrentes de múltiplas instâncias de aplicação
atendendo contas de autoatendimento.

### Exclusão lógica

O sistema opera com dois modos dependendo do usuário de banco:
- **`sgisis`** (usuário da aplicação): proibido de fazer `DELETE` físico — deve preencher
  `deleted_by`. A trigger de auditoria detecta o `deleted_by` preenchido e registra
  operação `'E'` na tabela audit, depois remove a linha fisicamente.
- **Outros usuários**: `DELETE` físico é permitido e auditado normalmente.

## Sistema de auditoria

Cada tabela de negócio possui uma tabela espelho em `audit.{schema}_{tabela}`. A tabela
audit:
- Não tem campos de auditoria de escrita (`created_by`, etc.) — apenas os três de
  leitura: `usuario_audit`, `oper_audit` (`I`/`A`/`E`), `dh_audit`
- Não tem constraints
- Tem dois índices compostos padrão: `(dh_audit, oper_audit, usuario_audit)` e
  `(dh_audit, usuario_audit, oper_audit)`

As cinco triggers de auditoria em cada tabela:

```sql
create trigger audit_bi before insert on schema.tabela for each row execute function audit.func_audit_before();
create trigger audit_bu before update on schema.tabela for each row execute function audit.func_audit_before();
create trigger audit_ai after insert  on schema.tabela for each row execute function audit.func_audit_after();
create trigger audit_au after update  on schema.tabela for each row execute function audit.func_audit_after();
create trigger audit_ad after delete  on schema.tabela for each row execute function audit.func_audit_after();
```

`audit.func_audit_before()` — normaliza `created_by`/`updated_by` e ignora updates sem
mudança real (comparação JSON excluindo os campos de trilha).

`audit.func_audit_after()` — grava o snapshot na tabela audit via
`jsonb_populate_record` dinâmico, usando `TG_TABLE_SCHEMA || '_' || TG_TABLE_NAME` para
resolver o nome da tabela audit.

`audit.log_acessos` é a exceção: não é espelho de tabela de negócio (vive só em
`audit`), registra acessos da aplicação diretamente (sem trigger de auditoria própria).
`audit.func_parse_user_agent()` ajuda a extrair navegador/SO dela para relatórios.

## Módulo Administração (`adm`)

### `adm.contas` — o tenant

Uma conta é uma empresa privada cadastrada via autoatendimento: `cnpj`, `razao_social`,
`nome_fantasia`, `email_contato`, `telefone`, `status` (`trial`/`ativo`/`suspenso`/
`cancelado`), `trial_expira_em`. CNPJ validado com dígito verificador via
`adm.func_valida_cnpj()` (idem `adm.usuarios.cpf` via `adm.func_valida_cpf()`) — ambas
portadas do schema `comum` do Sigein, pois são autocontidas e os CHECKs dependem delas.

### Habilitação de módulo → grupos de permissão automáticos

Ao inserir/atualizar `adm.contas_modulos` (conta X habilita módulo Y), a trigger
`contas_modulos_aiu` chama `adm.proc_gerar_grupos_permissoes_padroes(conta_id, modulo_id)`,
que cria os grupos "Administrador" (todos os módulos) e "Consultas e Relatórios" (demais
módulos, sem módulo 1), e vincula automaticamente os usuários administradores da conta.
Módulo `1` (Administração) é seed obrigatório desta migration inicial — outras regras de
negócio (`adm.trg_usuarios_bu`) assumem que ele existe.

### `adm.usuarios` é escopado por conta

Um usuário pertence a exatamente uma conta (`adm.usuarios.conta_id`, `not null references
adm.contas`). `login`, `email` e `cpf` são únicos **por conta**, não globalmente — duas
contas diferentes podem cada uma ter seu próprio usuário `admin`. Isso significa que
`usuario_login` sozinho não identifica mais um usuário: sempre usar `(conta_id, login)`
junto. Por isso `adm.grupos_permissoes_usuarios` carrega `conta_id` redundante (derivável
tanto de `grupo_permissao_id` quanto de `usuario_login`), sustentando duas FKs compostas
que impedem, a nível de banco, vincular um usuário a um grupo de permissão de outra
conta. Não há suporte nativo a "um usuário administrando várias contas" (ex.: contador
multi-cliente) — cada conta tem seus próprios usuários independentes.

## Roles e permissões

| Role | Tipo | Acesso |
|---|---|---|
| `sgidba` | login (DBA) | Dono dos schemas — acesso total (é o `POSTGRES_USER` do container, não criado por migration) |
| `sgisis` | login (aplicação) | `SELECT, INSERT, UPDATE, DELETE` nas tabelas de negócio; `SELECT, INSERT` nas tabelas audit |
| `sgitec` | grupo (sem login) | `SELECT, INSERT, UPDATE, DELETE` nas tabelas de negócio (exceto `adm.contas`/`adm.contas_modulos`, restritas — provisionar/desprovisionar conta é ação de app ou DBA); `SELECT` nas tabelas audit |
| `consulta` | login (somente leitura) | `SELECT` nas tabelas de negócio e audit |

`sgisis`, `sgitec` e `consulta` são criados de forma idempotente na própria migration
inicial (bloco `DO $$ ... $$`). Todo script que cria tabela deve incluir os grants para
os três roles.

## Infraestrutura local

O `sgdb_privado` **não tem Postgres próprio** — reaproveita o mesmo cluster que já roda
para o projeto `sgbd` (container `postgres-sigein`, rede Docker `sigein`). O isolamento
não vem de uma instância separada, vem de ser um banco de dados diferente
(`target`) dentro desse mesmo cluster — schemas (`adm`, `audit`) e roles concedidos são
por banco, então não colidem com o banco `sigein`. Roles de cluster (`sgidba`, `sgisis`,
`sgitec`, `consulta`) já existem por causa do `sgbd`; o bloco de bootstrap idempotente da
migration inicial só cria o que ainda não existir.

`docker-compose.yml` sobe um único serviço, `flyway-target`, que entra na rede externa
`sigein` e aplica `Scripts/` contra `postgres-sigein:5432/target`. Encoding do banco
`target` é UTF-8 (independente do banco `sigein`, que usa WIN1252/C por herança
histórica).

**Pré-requisito manual (uma vez só, antes do primeiro `docker compose up`):** o Flyway não
cria bancos de dados, só schemas dentro de um banco já existente. Criar o banco `target`
manualmente:

```bash
docker exec postgres-sigein psql -U sgidba -d postgres -c \
  "create database target encoding 'UTF8' template template0;"
```

## CI/CD

O GitHub Actions (`.github/workflows/deploy.yml`) faz build e push da imagem Flyway
customizada para `ghcr.io/sigeinbr/flyway-target:latest` a cada push em `main`. A imagem
empacota os scripts de `Scripts/` e o `run.sh`.
